# Lesson 30: Clusters, nodes and pods

**You'll learn:** what Kubernetes does and why (desired state, control loops), the control plane (API server, etcd, scheduler, controller manager) and nodes (kubelet, container runtime), kind (Kubernetes in Docker) and its nodes as containers, kubectl create cluster and the kubeconfig, contexts (kind-kind), kubectl cluster-info and config get-contexts, namespaces and -A, system pods in kube-system, kind load docker-image, the Pod object and its YAML manifest (apiVersion, kind, metadata, spec.containers), kubectl apply -f, get pods -o wide, describe and its events, kubectl logs, pod phases (Pending, ContainerCreating, Running, Completed, Error, CrashLoopBackOff), ErrImagePull and ImagePullBackOff, kubectl run with --restart=Never, deleting a bare pod, Docker Desktop's Kubernetes and Rancher, OrbStack.

▶ **Practise this lesson in the [sandbox](https://kishoremadanagopal.github.io/learning/shipping/#k8s-first-cluster)**: run every example and check your exercise answers.

## Key terms

- **Kubernetes:** a system that runs containers across machines and keeps them matching the objects you declare.
- **Control plane:** the API server, etcd, the scheduler and the controller manager.
- **Node:** a machine (or kind container) that runs pods; it has a kubelet and a container runtime.
- **kubelet:** the agent on each node that starts and watches the node's pods.
- **Pod:** the smallest unit Kubernetes runs: one or more containers sharing a network address and storage.
- **Manifest:** a YAML file describing an object, applied with kubectl apply.
- **kubeconfig and context:** the file (~/.kube/config) with cluster addresses and credentials, and the named pairing of a cluster with a user and namespace.
- **Namespace:** a group of objects inside a cluster; the default is `default`.
- **Event:** a record of something that happened to an object, shown at the bottom of kubectl describe.

You've packed the shop into an image and run it on one machine with Docker Compose. That works until the shop must run on many machines, restart itself when a process crashes, survive a machine failing, and roll out a new version without downtime. **Kubernetes** does that job: you describe what should be running, and it keeps the cluster matching that description.

You don't tell Kubernetes *how* to start a container on a particular machine. You tell it *what* you want ("three copies of the shop, reachable on port 80"), and control loops work out the rest, all the time, for as long as the cluster runs.

## Control plane and nodes

A cluster has two kinds of machines:

| Part | What it does |
|---|---|
| **control plane** | the API server (the only thing that talks to storage), **etcd** (the database holding every object), the **scheduler** (picks a node for each new pod), and the **controller manager** (the loops that keep reality matching the objects) |
| **nodes** (workers) | run your containers. Each has a **kubelet** (the agent that starts and watches pods), a container runtime (containerd) and networking |

Everything goes through the API server: `kubectl`, the controllers, the kubelets. You never change a container directly; you change an object, and the control loops act on it.

## A local cluster with kind

**kind** (Kubernetes IN Docker) runs each node of a cluster as a Docker container, which is how this course can run a real cluster in the sandbox. On your own computer it needs Docker (or Podman, Rancher Desktop, OrbStack) and works the same way.

```bash
const ordersFile = "data/orders.jsonl";
fs.mkdirSync("data", { recursive: true });

  console.log(`${req.method} ${req.url}`);
  if (req.url === "/") {
    res.end(`Welcome to ${shopName}!\n`);
  } else if (req.url === "/prices") {
    res.setHeader("Content-Type", "application/json");
    res.end(JSON.stringify(PRICES) + "\n");
  } else if (req.url === "/health") {
    res.end("ok\n");
  } else if (req.url === "/orders" && req.method === "POST") {
    let body = "";
    req.on("data", (chunk) => (body += chunk));
    req.on("end", () => {
      const order = JSON.parse(body);    // a body that isn't JSON throws here
      const line = JSON.stringify({ items: order.items, total: total(order.items) });
      fs.appendFileSync(ordersFile, line + "\n");
      res.statusCode = 201;
      res.end(line + "\n");
    });
  } else if (req.url === "/orders") {
    res.end(fs.existsSync(ordersFile) ? fs.readFileSync(ordersFile, "utf8") : "");
  } else {
    res.statusCode = 404;
    res.end("Not found\n");
  }
});

server.listen(port, () => console.log(`Shop listening on port ${port}`));
EOF
```

## A pod

A **pod** is the smallest unit Kubernetes runs: one or more containers that share a network address and storage. Almost always one container per pod. You describe a pod in a YAML **manifest**:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: shop-pod
  labels:
    app: shop
spec:
  containers:
    - name: shop
      image: shop:1.0
      ports:
        - containerPort: 3000
```

- `apiVersion` and `kind` say which type of object this is.
- `metadata.name` is the object's name, unique within its kind and namespace; `labels` are key–value tags you use to select objects later (lesson 32).
- `spec` is what you want: here, one container from `shop:1.0`. `containerPort` documents the port the process listens on; it doesn't publish it.

Write the manifest to a file and apply it. `kubectl apply` creates the object, or updates it if it already exists:


- `get pods` shows READY (containers ready out of total), STATUS, RESTARTS and AGE; `-o wide` adds the pod's IP and node.
- `describe` prints everything about the pod, including its **events** at the bottom: the scheduler's choice of node, the image pull, each container start. When something's wrong, the events say why.
- `logs` prints what the container wrote to standard output, like `docker logs`.

Pod phases you'll see: `Pending` (waiting for a node or an image), `ContainerCreating` (pulling and starting), `Running`, `Completed` (finished successfully, for jobs), and `Error` or `CrashLoopBackOff` (the container failed and is restarted with growing delays). A missing image shows up as `ErrImagePull` and then `ImagePullBackOff`:

## Try it on your own computer

- Install kind from [kind.sigs.k8s.io](https://kind.sigs.k8s.io/docs/user/quick-start/) and kubectl from [kubernetes.io](https://kubernetes.io/docs/tasks/tools/). Docker must be running.
- Docker Desktop can also run a single-node cluster: turn on Kubernetes in its settings. Use `kubectl config use-context docker-desktop` to switch to it.
- `kubectl explain pod.spec.containers` documents every field, straight from the cluster's API.

## At a glance

| Task | Command | What it changes | How to undo |
|---|---|---|---|
| Create a local cluster | kind create cluster | creates containers and a context | kind delete cluster |
| Apply a manifest | kubectl apply -f FILE.yaml | creates or updates objects | kubectl delete -f FILE.yaml |
| List pods | kubectl get pods (-o wide, -A) | nothing | — |
| Explain a pod's state | kubectl describe pod NAME | nothing | — |
| Read a container's output | kubectl logs NAME (--previous) | nothing | — |
| Run a one-off command | kubectl run NAME --image=IMAGE --restart=Never -- COMMAND | creates a pod | kubectl delete pod NAME |
| Copy a local image into kind | kind load docker-image IMAGE | copies into each node | — |
| Delete a pod | kubectl delete pod NAME | removes the pod (a Deployment replaces it) | — |

## Common mistakes

- Expecting a cluster node to see the images on your computer; load them with kind load, or pull them from a registry.
- Using tabs in YAML, which isn't allowed.
- Deleting a bare pod and expecting it to come back: only controllers recreate pods.
- Forgetting --restart=Never on kubectl run, so a one-off command is restarted again and again.
- Working in the wrong context: check kubectl config current-context before deleting anything.

- `apiVersion: v1` and `kind: Pod` say which object to create.
- `metadata.name: shop-pod` is its name; `labels` are optional here but useful later.
- `containers` lists one container: `name` for the container, `image` for what to run.
- `kubectl apply -f pod.yaml` creates the pod; `get pods` shows it is `Running`.

**Trace:** `pod/shop-pod created`, then `shop-pod   1/1   Running   0   …`.

**Common wrong approach:** writing the manifest with a tab indent. YAML forbids tabs; use spaces.

</details>

<details>
<summary>✅ 2. A one-off pod</summary>

```bash
kubectl run greeting --image=busybox:1.37 --restart=Never -- echo "hello from kubernetes"
kubectl logs greeting
```

**Line by line**

- `kubectl run greeting --image=busybox:1.37 --restart=Never -- echo "hello from kubernetes"` creates a pod whose one container runs `echo`.
- `kubectl logs greeting` prints the container's output.

**Trace:** `hello from kubernetes`.

**Common wrong approach:** leaving out `--restart=Never`. The pod then runs the command, exits, and is restarted over and over (CrashLoopBackOff is for failures; for a finished command the phase is Completed when the restart policy is Never).

</details>

## Quick quiz

1. What does a control loop in Kubernetes do?
   - A) It copies images from your computer into the cluster
   - B) It deletes pods that have been running for too long
   - C) It compares the objects you declared with what's running and acts to close the gap
   - D) It runs your containers once and then stops

2. Why does kind load docker-image exist?
   - A) It's required for every kubectl command
   - B) Kubernetes can't run images that were built with Docker
   - C) It makes containers start faster
   - D) Cluster nodes have their own image storage and can't see the images on your computer

3. A pod you created directly is deleted. What happens?
   - A) It moves to another node
   - B) Nothing: a bare pod isn't recreated, so it stays deleted
   - C) Kubernetes recreates it at once with the same name
   - D) It's restarted after 5 minutes

4. Which is the smallest unit Kubernetes runs?
   - A) A deployment
   - B) A node
   - C) A pod, which holds one or more containers that share a network address
   - D) A container

<details>
<summary>Quiz answers</summary>

1. **C) It compares the objects you declared with what's running and acts to close the gap**: Controllers run all the time, so the cluster keeps converging on the declared state.
2. **D) Cluster nodes have their own image storage and can't see the images on your computer**: Real clusters pull images from a registry; locally, kind copies them into the nodes.
3. **B) Nothing: a bare pod isn't recreated, so it stays deleted**: Controllers such as Deployments are what keep pods alive.
4. **C) A pod, which holds one or more containers that share a network address**: Pods share network and storage; most pods hold one container.

</details>
